Small AI that refuses rather than guesses, in your browser tab

Browser Swarm is a web page that runs a small AI model on your own computer. It is free and open source, and there is nothing to install. The one model is given seven job descriptions, like seven desks in an office. Each desk does one bounded job: answer from your documents, read a receipt total, sort a message, convert a date. And each one is checked before it may speak. If the check fails, you get an honest "I can't say" in place of a confident wrong answer. The checks are not perfect, and this page counts every wrong answer that got through. Nothing you type leaves your device. Nothing is charged per question.

It will not out-think a large cloud model, and this page shows exactly where it loses. What it is built for is the one number that decides whether you can trust AI with routine work: how often it delivers a wrong answer as if it were right. That is the silent-failure rate. It was measured on 410 tasks, with every rule written down and sealed before the test was run, and you can re-run it on your own machine.

Words on this page
  • Silent failure: a wrong answer delivered as if it were right. A refusal is never one.
  • The swarm, a desk: the one small model given seven job descriptions. A desk (the code calls it a cell) is one of them: what it accepts, what it asks the model, and how its answer is checked.
  • Bounded work: a routine job with a right answer that can be checked. Here: answering from documents, reading a receipt total, naming a banking request, routing a message, converting a date, converting an amount, drafting a refund letter.
  • Hard work: open general-knowledge and reasoning questions. They are in the test so the swarm's losses show.
  • Lane check: the test before the model runs: does this job belong to this desk? If not, the model is never asked.
  • Compliance check (the code calls it a judge): the test after the model: code that checks the answer against its source. It is never another model.
  • Raw, or unchecked: the same model with every reply delivered as it comes. Gated: behind the checks.
  • Grounding: a released answer can be traced to its source by a check anyone can run: the characters in the paragraph, the line on the receipt.
  • Sealed: frozen by a fingerprint (a SHA-256 hash) before the test, so nothing could be adjusted after the results were seen.
  • p (exact McNemar test): a test on the tasks where two arms disagree. Below 0.05, the gap is unlikely to be chance.

The six numbers

The test is 410 tasks: 60 questions about a set of documents, 50 receipts, 60 banking messages, 60 messages to route, 25 dates, 25 amounts, 50 refund letters, and 80 hard general questions the swarm is expected to refuse. They were drawn by a fixed seed from published datasets (SQuAD 2.0, CORD, Banking77, CLINC150 and MMLU) plus three generated kinds. None was hand-picked. Each arm answered the same tasks. The swarm is a 1B model in a browser tab, behind its checks. 1B raw is the same model on the same prompts, with every reply delivered unchecked. 7B raw is a model seven times larger, run on a laptop processor. 7B gated is that larger model behind the same checks: the fair comparison, which shows how much of the result comes from the checks rather than the model. Frontier raw is a large cloud model, Claude Opus 5.5 at medium effort, given the same prompts unchecked. It was called through Kar's spend wall under its owner's written approval, with a $4 cap, on a seeded sample of the test tasks, so its column covers the tasks the caps allowed.

How it works

One base model, many specialists. A specialist, or cell, is not a second model. It is a card the base model is run under: what it accepts, what it asks the model, and how its answer is checked. Every request goes through the same four steps, and only the last can release anything.

  1. The conductor reads the request and picks the cell whose declared lane covers at least half of its words. If none fits, it refuses and names who to escalate to. This is the Estate Genome's conductor, unchanged.
  2. The lane check runs before the model. Know the boundary first. The documents cell retrieves the best-matching paragraph and refuses if no paragraph clears its bar. It also refuses a paragraph whose SHA-256 no longer matches the signed corpus, and two near-identical paragraphs that disagree. If the lane says no, the model is never asked.
  3. The base model answers under the cell's card. Every cell shares this one model, so the swarm costs the memory of one model.
  4. The judge checks the answer with code, never with a model. For documents: the answer must be the source's own words, in the sentence that best matches the question, carrying enough of the question's words, and not in a sentence that gives orders. For a receipt: the number must be printed on a total line. For an intent or a department: the model must agree with an independent word index built from training data. For a date or an amount: it is read back against the words it came from. For a letter: every fact must be word for word, and no other number may appear. Only a verified answer is released. Everything else is withheld, with the reason.

Attacks on the checks

A check that can be fooled is worse than none, because it creates false trust. So each defence was attacked on 40 fresh questions it had never seen. An attack succeeds when the swarm releases the false answer. The verdict uses the runner that was sealed before the test: the same 1B model served on this laptop. The same attacks run in the browser tab are shown beside it, and you can run them on your own device in step 6.

not measured yet

The limit, stated plainly. The checks prove that an answer is your source's own words and fits the question. They cannot know whether the source is true. If a lie is written into the source itself and signed (A2b), the swarm repeats it faithfully. Keeping a source honest is a separate job, done by whoever signs the corpus.

How it grows without getting bigger

  • By corpus (built): add documents and sign them. Knowledge lives in your files, not in the model's weights. Step 4 shows it.
  • By cell (built): a new specialist is a new card, with a lane, a prompt and a judge. It is admitted only if its judge can tell right from wrong.
  • By tier (built): the same cells run over a 3B model on a desktop. Only the 1B tier was measured. This build has no lighter phone tier, because WebLLM's 0.5B build needs 945 MB, more than the 1B.
  • By adapter, distillation and federation (not built): see the blueprint above.

Adoption: what it does for your business

Where it fits

Bounded, repeated work where a wrong answer costs more than a pause. Answering staff questions from your own policy documents. Reading totals off receipts and invoices. Routing customer messages. Normalising dates and amounts. Filling template letters from a record. The swarm does this on the laptops you already own, and says plainly when it cannot. Expect it to hand back more jobs than it completes: the per-kind table shows how many, for each kind of work.

Where it does not

Open-ended reasoning, general knowledge and anything creative. On those, a small model loses (claim B2, shown above), and the swarm refuses them rather than guess. Keep a person, or a larger model, for that work.

Rolling it out

  1. Pick one bounded job and collect 50 or more real examples with their right answers. Those become your own test set.
  2. Sign your corpus (for documents) or build the word index (for labels) from your own data.
  3. Run your test set on this page, on a staff laptop, and read your own six numbers. Decide whether its refusal rate is one you can live with.
  4. Put it in front of staff with the refusals routed to a person. Every refusal says why, and that list becomes your backlog.
  5. Host it yourself. Copy the repository's files to any web server on your intranet, or fork it and switch on GitHub Pages. There is no build step and no server code. Open index.html over https (WebGPU needs a secure address). After the first load it works offline.

Security, compliance and data protection

  • No processing leaves the device. The model runs in the browser on WebGPU. The page loads its model from the MLC project's published build once, then works offline. It sends nothing back anywhere.
  • No personal data is collected by us. There is no account, analytics or telemetry. Results are saved only if you press "Save my results", to your own disk.
  • Supply chain. The page loads one library, WebLLM 0.2.79, pinned to an exact version. Its code is MIT-licensed and public, and its decision code is mutation-gated with witness v0.6.
  • Where your data is, exactly. Processed: in this tab's memory and on your own GPU. Stored: the model in this browser's cache, and a saved run of your own in this browser's local storage, for this site only. Sent: nothing. Fetched, at load time only: the page from GitHub Pages, the WebLLM library from the jsDelivr CDN, the model's weights from the MLC project's repository on Hugging Face, and its compiled code from the MLC project's repository on GitHub.
  • Audit trail. Every decision is a record: the request, the desk, the lane check's result, the model's exact reply, the check's verdict and reason, and for a released fact its source and character positions. "Save my results" writes the records to a file on your disk, and step 7 shows how any record is re-decided from its reply. There is no central log, because nothing is sent anywhere.
  • Model integrity: a limit. WebLLM fetches the model files by name and does not check them against a fingerprint, and neither does this page. For a regulated deployment, host the model files on your own server and pin them.
  • Not a certification. This page is not a compliance certificate. What it gives a reviewer is evidence: no data leaves the device, every decision can be replayed, and the failure rate is measured and published. Your own data-protection assessment still applies.
  • Assurance. The claims were registered before the test, the code was frozen by hash before the test, and every published decision can be replayed in your browser.

Updates and upkeep

Nothing updates by itself. The page pins its library and its model by exact version. To change the model, a desk or a check, you edit the files, re-run your test set, and publish again; a test fails if any sealed file changes without a new seal. A new desk is admitted only when its check can tell a right answer from a wrong one.

White paper: the reef, not the cathedral

The problem. A large cloud model cannot run on your own device, cannot run without a meter, cannot answer without a network round trip, and cannot tell you in advance what it will refuse. Above all, it cannot show you how often it is confidently wrong. None of that is about how clever it is.

The idea. Use many small, bounded specialists instead of one large model. Take knowledge out of the weights and keep it in a signed corpus. Take trust out of the model and put it in checks written as code. A small model loses on open questions, so it does not take them. On bounded work, a small model behind good checks releases few wrong answers and says when it cannot answer. The measured cost is that it answers far less.

The method. Claims and bars were written first (seal 1). The cells were built on a dev split and a separate tuning pool. Each release rule was chosen there by one stated criterion: the most right answers minus twice the silent failures. Then everything was frozen by hash (seal 2), and the 410-task test split and 40 fresh attacks were read once. The suite includes work the swarm should lose, so the losses are visible.

The result. not measured yet

What it shows, and what it does not. The checks, not the model, drive silent failures down: the 7B gated arm shows the same checks on a larger model. The small model's part is to be free, private and fast enough. On routing, the word index alone outscores the 1B model. The swarm's value there is the agreement between the two, not the model by itself. Nothing here shows that a small model knows or reasons as well as a large one. B2 shows that it does not.
